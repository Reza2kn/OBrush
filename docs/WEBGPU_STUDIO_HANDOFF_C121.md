# C121: WebGPU sparse result into the normal studio document

The normal OBrush browser app now exposes a one-use resident capture/commit bridge. It captures its **actual shared-core document** as a versioned `.obrush` project, assigns an opaque string token, and accepts a GPU-produced sparse result only for that capture. The core checks current subtool, pose, complete mesh fingerprint, finite positions, mask protection, surface folds, open edits and redo ownership before a single undoable mesh replacement. The app rejects handoff during an active stroke, queued dabs, transform, region selection, topology job, UV bake job or pending SGL export. Any normal document publication invalidates an outstanding capture. A successful commit increments the app revision and requests its ordinary viewport redraw.

The official `scripts/build-web.sh` now packages the GPU WASM module alongside the existing app, using the lockfile-matched `wasm-bindgen` CLI 0.2.129. The GPU module loads only when requested; the normal app still starts with WebGL2. A frozen copy of the official build was served in a fresh owned Chrome session. On OBrush's actual startup sphere (**40,962 vertices / 81,920 triangles**), a separate offscreen WebGPU point pass returned **2,511 changed vertices / 50,220 sparse bytes** with no full-position readback. The normal studio rejected a nonfinite result while retaining the capture, accepted the valid result, rejected reuse of its token, changed its complete saved project hash, and redrew the visible sphere. The 590×590 sphere review region changed **44,103 pixels**.

A second fresh browser run used the normal canvas keyboard route: Command+Z restored every RGB pixel in that sphere region to the pre-edit frame, and Command+Shift+Z restored every pixel to the edited frame. The bridge's Rust tests also compare complete project JSON through Undo/Redo and check cancellation, stale tokens and invalid bytes. The browser mapped `[4,4,50220,4]` bytes for the GPU failure word, count, compact result and post-count; no GPU full-position map, JavaScript exception, console error or external request appeared. Both owned browser processes exited zero and their servers closed.

This is **a real studio document/history handoff, not a production WebGPU sculpting mode**. The point pass runs on a separate offscreen WebGPU canvas, initiated through diagnostic host functions; normal pointer brushes, picking and the visible renderer remain CPU/WASM plus WebGL2. After accepting the sparse result, the app still validates and refreshes its CPU mesh and WebGL buffers. No end-to-end or sustained responsiveness improvement is claimed, and this point pass does not match SculptGL or ZBrush brush response. A future resident viewport must own actual studio pointer input, current-subtool selection, drawing, CPU fallback, device loss and history synchronization before the unchanged browser performance matrix can be rerun as a product gate.
