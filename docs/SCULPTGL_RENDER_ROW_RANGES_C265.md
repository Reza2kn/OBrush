# C265: bounded exact-row renderer trial

This trial starts from OBrush commit `71837a8a17c400f8ebfeeecba95083c7cf36f34a` and the unchanged C264 million-vertex Source Brush protocol in [SCULPTGL_MILLION_CURRENT_C264.md](SCULPTGL_MILLION_CURRENT_C264.md). This page records the prediction before the candidate is built or measured. It does not establish SculptGL parity.

The current selected-chunk renderer detects bitwise-changed 40-byte rows but uploads an entire 2,048-row chunk when any row differs. Its C264 browser trace counted 956 selected-chunk witness uploads and 3.45 GB of VBO `bufferSubData` traffic over the 60-second run. The candidate publishes exact contiguous changed-row runs inside selected chunks, coalesces the smallest gaps to at most 128 GL calls, and chooses the prior chunk plan when the row plan saves less than 4 KiB per additional GL call. Both plans retain the 128-changed-chunk full-buffer fallback. The VBO cache, mask/material checks, bounds, undo and file paths remain unchanged.

Predictions to test on the frozen C264 harness: VBO `bufferSubData` bytes should fall below 3.45 GB while calls stay at most 128 per selected upload. The full row scan may cost more CPU than the old per-chunk short circuit. Record the new `selected_row_scan` timing, existing `mesh_upload` and renderer callback timing, VBO bytes and calls, RAF P95 and release acknowledgment; reject a byte-only win if callback time worsens. The one-run RAF and release gates might still fail because shared-core geometry dominates many callbacks. A candidate is acceptable only if ordinary browser `Save`, `Undo`, `Redo` and the 16-check source-file audit pass; a byte reduction alone is not a responsiveness or reference-parity claim. Report the same before/after protocol and hashes, including failed checks.

## Rejected 128-call result

The normal Chrome run completed 919 Source dabs with no recorder overflow, console error or GL error. The selected-row scan averaged 4.990 ms over 919 samples. On the actual geometry VBO (buffer 7), `bufferSubData` wrote 207,667,520 bytes in 79,965 calls during the active minute, versus about 3.45 GB in 956 calls in C264. The large reduction in transferred bytes came with roughly 87 GL calls per dab. Mesh-upload CPU mean was 9.458 ms (C264: 10.328 ms), but the active RAF interval P95 was **83.3 ms** (C264: 66.7 ms), app RAF callback CPU P95 was **73.4 ms** (C264: 68.0 ms), and release acknowledgment was 146.0 ms. All four responsiveness gates remain failed. The different delivered-dab counts and separate runs rule out a causal timing ratio, but this candidate is not acceptable as a browser responsiveness fix.
