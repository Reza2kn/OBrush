# C140 queued-brush CPU timing boundary

The ordinary studio now reports cumulative, last, maximum and mean wall time for processed ordinary, Source Paint and Source geometry dabs, plus the release queue. The read-only `window.obrushSculptMetrics()` route exposes these counters in the browser. They use the same queue that owns normal input and do not change brush mathematics, document history or rendering. Saturating counters keep long sessions from overflowing.

On the official browser build, an isolated Chrome run delivered fresh-sphere stationary pen and mouse contacts through the normal canvas. The zero-pressure pen produced no edit; quarter/full-pressure pen and default mouse each changed 632 original vertices, cleared the pending queue, and had actual packed GPU geometry matching the saved mesh. Their recorded ordinary-dab wall times were 1.3, 13.1, 8.1 and 7.6 ms respectively. Each case had one processed dab, so these are **individual observations**, not a throughput or latency distribution. The first value includes an ineffective zero-pressure dab. Release queue observations were 1.1, 0.2, 0.0 and 0.0 ms at the browser clock's available resolution.

The same legacy pressure/alpha browser harness then failed at its first alpha case: `Alpha import request is stale`. Its previous four cases and exact served-WASM hash remain recorded in the failed result. This C140 evidence is therefore a **partial brush-host smoke**, not a full pressure/alpha acceptance pass. The full workspace test suite, strict native/WASM Clippy, official web build and signed macOS package passed after this source change. No pinned SculptGL or ZBrush reference operation was run for C140.

These counters isolate the time inside queued application. They omit input delivery, stroke preparation outside the queue, renderer packing/uploads/draw, asynchronous GPU completion and input-to-photon delay. The Source-geometry counter has not yet been sampled on the million-vertex sustained cohort. That unchanged cohort still fails responsiveness; C140 does not establish a speedup or production WebGPU integration. The next useful measurement is the **same** 10K/100K/1M Source-brush trace with this counter, frame times and WebGL uploads collected together, followed by a GPU-resident brush design that preserves the shared-core geometry and history contract.
