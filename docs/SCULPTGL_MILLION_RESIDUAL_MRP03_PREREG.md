# MRP03: read-only million-vertex residual attribution

MRP02's [rejected certified-hover trial](SCULPTGL_MILLION_CERTIFIED_HOVER_MRP02_RESULT.md) is the motivation, not a promoted product baseline. Its temporary uninstrumented hover candidate reduced active RAF P95 from 66.7 to 33.4 ms and app callback CPU P95 from 62.4 to 35.1 ms, yet failed all four frozen responsiveness gates. The 999,002-vertex SGL fixture SHA-256 remains `dfb5316f62e392e633f03cb662dcb12215ed165a71a9ae72a3fd639528731afe`; the original 60-second/400-requested-moves/s protocol SHA-256 remains `234870ed03a240931a22f421968917efaeed8becc1df834c998bbe3e9c101a33`. The original active-recorder gates remain RAF P95 ≤33.34 ms, RAF maximum ≤250 ms, app callback CPU P95 ≤16.667 ms, and release acknowledgement ≤100 ms. This plan neither changes those thresholds nor accepts the MRP02 candidate. Its own read-only measurements cannot establish SculptGL or ZBrush parity.

## Existing evidence and competing causes

The MRP02 candidate's 1,159 applied dabs averaged 22.19 ms in `source_geometry` per dab. Nested within that were 6.72 ms retained mesh matching, 6.76 ms state advancement, 1.75 ms normal refresh, and other smaller stages. The renderer callback averaged 7.91 ms over 3,467 callbacks, including 4.45 ms mesh upload and 1.70 ms scene admission **over all callbacks**; dividing by upload-bearing callbacks could change those conditional means. These are different sample populations and overlapping scopes, so none is summed into a purported frame cost. The 35.1 ms app callback CPU P95 could reflect geometry plus upload in the same frame, but that co-occurrence has not been measured. MRP02's retained browser `appRAF` rows place the frozen 600.0 ms maximum at page timestamps 37,871.2 → 38,471.2 ms. The pointer-down event was recorded at 37,872.3 ms, so the gap belongs to **initial press**, before the first scheduled move. The runner's Node clock cannot be compared directly to page timestamps: its captured alignment puts that first move at about page time 38,587.5 ms. The largest gap between scheduled first move and release was another 400.1 ms at page time 38,637.8 → 39,037.9 ms. The diagnostic therefore needs separate initial-press, early-stroke and steady-stroke attribution; no particular function owns either long gap yet.

The release acknowledgement was 106.963708 ms after request. Inspection of the exact pinned runner (`large-perf-sustained.mjs`, SHA-256 `fca0fbbd0a69c3e642e0b1271cfd09e0a0f5834b2032e8562cff9adf93f3c87e`) shows that this is the time to await Chrome's `Input.dispatchMouseEvent` release command, **not** a queue-empty poll. The first retained tail queue observation is about 110.25 ms after request and already reports zero pending dabs and one released stroke. Retained candidate `appRAF` rows near release show sub-millisecond callback CPU and roughly 16.7 ms cadence; the core release timing sample reports 0 ms. Whether the command acknowledgement is delayed by prior input commands, browser dispatch, a frame boundary, or other host work is unknown. The original ≤100 ms gate remains failed. MRP03 will not substitute the first positive queue poll for the original command acknowledgement.

## Freeze and read-only protocol

Wait for the active feature/build lanes to finish, then pin one exact integrated product commit, browser version, owned runner, source tree, portable WASM, fixture and protocol hashes. Preserve the MRP02 rejected patch SHA-256 `b30c476a7fc53fd965afece685bda8bcd66311607bd76f63fb474e822ab2e300` as a historical input only. If it does not apply unchanged to the pinned product, record the necessary diff and revalidate its same-state hit and file behavior before using a temporary hover-free diagnostic build. Run an unchanged-product control and, if the temporary hover-free build is valid, an uninstrumented hover-free control. Only then add a **read-only** timing probe to that identical hover-free source and run the same owned normal-browser cohort. Do not modify geometry, queue policy, frame scheduling, renderer state, packet bytes, thresholds or the runner's event schedule. Preserve every receipt, including compile, audit, browser and gate failures. Different delivered dab counts make whole-cohort timings observational, not matched-state causal evidence.

The probe records a bounded per-frame scalar trace with a monotonically increasing frame ID and event/callback timestamps. It measures `App::update` panel, `viewport`, `process_dabs`, Source frame preparation, rendered-scene refresh, cursor path and paint-callback handoff as distinct nested phases; the actual renderer callback measures scene admission, mesh upload, draw and residual. It records dab count and changed-revision count per frame, and renderer upload-bearing versus idle frames. It does not serialize meshes, mutate state, force extra repaints or perform expensive per-frame JSON formatting. A fixed bound and overflow bit make the trace fail closed if it cannot retain the complete 60-second period. Browser `appRAF`, input events, long tasks and CDP timestamps remain separate witnesses; align them using monotonic callback/event times and frame IDs, and report any clock uncertainty. Report per-phase count, conditional P50/P95/max and a same-frame correlation table for geometry, upload, update total and RAF CPU. Never add nested means or compare unmatched sample populations.

Classify each RAF interval as before pointer-down, initial press before the first scheduled move, early stroke, steady stroke or release tail, first aligning the runner's Node clock with browser `performance.now()` and reporting the alignment error. Retain the original all-active gate verdict. For the initial-press 600 ms and early-stroke 400 ms classes, capture read-only host/JS long-task and requestAnimationFrame scheduling evidence around each exact gap and distinguish callback CPU from time outside callbacks. For release, record separate timestamps for requested mouse release, Chrome command acknowledgement, browser delivery, egui observation, final endpoint acceptance, queue empty, one-step history commit, renderer presentation and independent poll observation. Do not substitute an earlier timestamp for the frozen release-command acknowledgement gate; report both the original value and component intervals. If an event is unobserved or clock alignment fails, leave its cause unknown.

Before interpreting timing, run the independent complete 17-check public-file/history/shape auditor on each owned browser cohort. Required are byte-exact Before/Undo and After/Stable/Redo, one-step history, finite geometry, unchanged non-position channels/directed faces, useful edits, and no new affected-face degeneration/reversal. Require zero app/GL/queue-overflow errors, visible browser, bounded memory and clean owned process/server exit. A future product candidate additionally needs an independent actual GPU VBO position and Source display-normal word oracle, which MRP02 lacked. Keep the current official build restored after a temporary diagnostic.

## Admission for a later product experiment

MRP03 itself admits no optimization. A later candidate requires a separate preregistration naming a single measured stage that costs ≥10 ms per useful frame or ≥25% of callback CPU in matching pressed frames, an identical-state native/WASM microbenchmark predicting at least 5 ms reduction without worse peak memory, and exact same-state geometry/hit/display differentials. Its owned browser run must pass all 17 public-file/history/shape checks, the actual GPU words, unchanged endpoint and errors, and show no regression against the **matched** control in release, RAF P95/max or app CPU P95. Full responsiveness promotion still requires all four original global gates. If a long gap or release acknowledgement is caused by the harness or its observer, record that finding without quietly weakening the frozen contract; any revised user-facing latency contract would need an explicit, separately frozen comparison.
